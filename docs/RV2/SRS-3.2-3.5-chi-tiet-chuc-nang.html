3.2 Record Speech

The feature a Speaker uses to turn an assigned sentence pair into two approved recordings: check the sentence, read it aloud, and submit. The unit of work is the pair — the code-switched sentence and its pure-Vietnamese equivalent — and both halves are read by the same voice (BR-10).

3.2.1 Review Text

Function trigger. Speaker Home → Start recording. The screen also reopens by itself after every successful submission, so the Speaker moves straight to the next pair. The client calls GET /api/speaker/scripts/next, optionally carrying the chosen task.

Function description. Actor: Speaker. Purpose: let the Speaker judge the sentence before spending effort recording it, and give them a route to fix or report a bad one. The screen shows the code-switched sentence, its Vietnamese equivalent, the word-level alignment, the topic, and the recording guidance. Four actions are offered: record this pair, propose an edit, report an error, or switch to another assigned task. Data processing: the server claims the next sentence for this Speaker from the work queue through the database function fn_queue_claim_next, which uses FOR UPDATE SKIP LOCKED so two Speakers are never handed the same pair; the claim expires by itself after 30 minutes (BR-20).

If the Speaker walks away, the claim expires and the sentence returns to the queue on its own — no cleanup job runs (BR-20). If the Speaker reports an error or proposes an edit, the sentence is held out of the recording queue until a Reviewer decides (BR-18, BR-19).

3.2.2 Record Speech

Function trigger. Review Text → Record, once for the code-switched half and once for the Vietnamese half. This step runs entirely in the browser; no request is sent yet.

Function description. Actor: Speaker. Purpose: capture the audio and let the Speaker judge it before anyone else has to. The screen shows the sentence being read, a record/stop control, a playback control and a re-record control. The browser captures audio through the media API, so the Speaker must grant microphone permission once per browser. The guidance shown here uses the same thresholds the server will apply, so a take that looks acceptable on screen is not rejected a second later for a reason the Speaker could not see.

3.2.3 Submit Recording

Function trigger. Record Speech → Submit. The client sends POST /api/recordings as a multipart request carrying the audio file, the sentence identifier, the variant (cs or vi) and the task.

Function description. Actor: Speaker. Purpose: store the take and put it in front of reviewers. Data processing, in order: the server checks the sentence is recordable by this Speaker in this task; converts the upload to 16 kHz mono WAV and measures it with FFmpeg/FFprobe; compares the measurements with the thresholds above; uploads the file to object storage; generates the recording identifier; inserts the row; then recalculates task progress and pushes the recording into the review tasks of the same campaign.

3.3 Review Recordings

The feature a Reviewer uses to decide whether a recording may enter the corpus. Reviews are blind: a Reviewer never sees how others voted before submitting (review.default_blind is true).

3.3.1 Review Task List

Function trigger. Review Dashboard → My tasks, then a recording task. The client calls GET /api/reviewer/tasks/{taskId}/recordings. A Reviewer with no particular task in mind can instead ask for the next item anywhere with GET /api/reviewer/recordings/next.

Function description. Actor: Reviewer. Purpose: show what is waiting, how much of the target is done, and how long remains to the deadline. The list is grouped by sentence pair, not by individual take, because a decision on one half affects the other (BR-15); each row shows both takes and marks which one still needs this Reviewer's vote.

3.3.3 Submit Review Decision

Function trigger. Review Recording → Approve, or Reject followed by the Reject Reason dialog. The client sends POST /api/recordings/{id}/reviews.

Function description. Actor: Reviewer. Purpose: record one independent vote and, when the votes are decisive, settle the recording. The decision itself is taken in the database: a trigger on the review table recomputes the outcome after each insert, and the service reads back what the database decided rather than computing it. Concurrent voters are serialised by a row lock, so the loser of a race is told the round moved instead of having a vote written into the wrong round.

3.5 Manage Text Data

The feature an Administrator uses to build and maintain the sentence corpus that everything else consumes.

3.5.1 Browse and Edit Sentences

Function trigger. Admin Dashboard → Text Data, which calls GET /api/scripts with search, filter and paging. Editing one sentence sends PUT /api/scripts/{id}; POST /api/scripts/{id}/deactivate and /reactivate take a sentence out of circulation and back.
