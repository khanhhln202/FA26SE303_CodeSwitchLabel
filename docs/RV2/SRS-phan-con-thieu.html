4.1 External Interfaces

User interface. A browser-based single-page application. Speakers need microphone permission; all other work needs only a browser. The interface is in Vietnamese.

Hardware interface. The speaker's microphone, reached through the browser's media API. No other hardware is required.

Software interfaces.

InterfaceProtocolPurpose
REST APIHTTPS/JSON, bearer tokenEvery client operation. The contract is published as OpenAPI and browsable through Swagger UI.
Object storageS3 protocolAudio storage. Playback uses presigned links valid for 15 minutes; the application never proxies audio bytes.
PostgreSQLTCP, pooled connectionsAll persistent data. Business invariants are enforced inside the database, not only in application code.
FFmpeg / FFprobeLocal processAudio measurement during automatic QC.

Communication interface. HTTPS only, with certificates obtained and renewed automatically. Uploads are capped at 25 MB per request at the reverse proxy.

4.2 Quality Attributes

4.2.1 Usability

  • A speaker who has signed in can reach the recording screen and submit a first pair without training; the screen shows the sentence, the microphone control and the remaining takes.
  • Every rejection reaches the speaker as a sentence in Vietnamese, not a code: a rejected recording carries the reviewer's comment, or the description of the reasons chosen when no comment was written.
  • The system never reports a bare failure where it can state the cause: an action that cannot be performed returns a message naming the rule that blocked it (see the message list in 5.3).
  • Recording guidance (maximum duration, acceptable silence at either end) is shown to the speaker before they record, using the same thresholds the automatic QC applies.

4.2.2 Reliability

  • Availability. The service targets availability during working hours; the deployment is a single virtual machine, so planned restarts are the main interruption and last under a minute.
  • Correctness over availability. Every business invariant that matters is enforced by the database — identifier format, one voice per pair, one active take per variant, duplicate sentences, dataset immutability — so a defect in application code, or a direct SQL write, cannot corrupt the corpus.
  • Recovery. The database is dumped nightly and the archives are rotated; a copy is kept off the server. A deployment takes a backup before it applies any migration, and stops rather than attempting an automatic restore if a step fails.
  • Defect control. The solution is built with compiler warnings treated as errors and ships only when the full automated test suite passes — currently 516 test cases, all passing, run against a real PostgreSQL instance rather than a stub.
  • Data integrity under concurrency. Operations that two people can perform at the same moment — claiming a sentence, submitting the deciding review — are serialised with row locks and guarded by unique indexes, so a race produces a clear refusal rather than duplicated or lost work.

4.2.3 Performance

  • Response time. Interactive requests complete well inside one second on the current deployment; audio never passes through the application, so playback and upload speed are bounded by object storage rather than by the API.
  • Audio QC. Measurement of a take completes within a few seconds of upload and runs before the recording becomes visible to reviewers.
  • Capacity. The corpus currently holds 14,037 sentence pairs with 14,008 approved, across 13 campaigns and 49 tasks. An import accepts up to 100,000 sentences per batch.
  • Pagination. Every list endpoint is paginated with a maximum page size of 100 rows, so no screen can ask the server for an unbounded result.
  • Queue fairness. A claimed work item is released after 30 minutes, bounding how long one abandoned claim can hold up the queue.

4.2.4 Security

  • Authentication is token-based; every endpoint except sign-in and speaker registration requires a valid token, and role requirements are declared per endpoint.
  • Passwords are stored hashed; a reset issues a temporary password rather than revealing the old one.
  • Audio is reachable only through short-lived presigned links, so a leaked link expires in minutes.
  • Changes to users, sentences, recordings, reviews, tasks, campaigns, proposals and datasets are written to an audit log.

4.2.5 Maintainability

  • The backend is layered API → Services → Repositories, and the database schema is the single source of truth for business invariants.
  • Schema changes ship as numbered migration files recorded in a ledger with checksums, applied automatically during deployment.
  • Diagrams for architecture, the entity model, ten state machines and four workflows are kept in the repository as text (docs/diagrams/), so they are versioned alongside the code they describe.

5.1 Business Rules

IDRule definition
BR-01A sentence pair consists of a code-switched sentence and its pure-Vietnamese equivalent; both are required and both carry [vi]/[en] segment tags.
BR-02A sentence identifier has the form s_ followed by 9 or 12 digits. The first digit is the number of embedded English words, the second is the topic (1 IT, 2 education, 3 daily life), the third is the English–Vietnamese relation (1 direct translation, 2 contains a proper noun); the rest is a serial number issued by the database.
BR-03A sentence may contain between one and nine English words.
BR-04The first three digits of a sentence identifier must agree with the sentence's own word count, topic and alignment; the agreement is checked again when the transaction commits.
BR-05Two sentences may not have the same code-switched content.
BR-06A sentence enters the pool as pending validation and becomes recordable only after a content review by a reviewer qualified for its topic.
BR-07Editing an approved sentence may not change the number of English words, the topic, or the English–Vietnamese relation, because all three are encoded in its identifier.
BR-08A sentence that already has recordings may not have its wording changed, because the existing audio would no longer match the transcript.
BR-09A recording identifier has the form r_cs_ or r_vi_ followed by the digits of its sentence, plus a take number for re-records; the prefix must match the variant and the digits must match the sentence.
BR-10Both halves of a sentence pair must be recorded by the same speaker.
BR-11A sentence pair may have at most one active recording per variant — that is, one take that is either awaiting review or approved.
BR-12Audio is accepted only within the configured duration, volume, peak and silence limits; a take outside them is stored as failed automatic QC and never reaches a reviewer.
BR-13A recording requires review.rounds_required independent blind reviews (currently 3). A reviewer may not review the same recording twice, and may not review their own recording.
BR-14The outcome is decided by majority as soon as one side reaches it; the remaining rounds are not required because they cannot change the result.
BR-15Rejecting one recording of a pair retires the other as well, so the speaker re-records the whole pair.
BR-16A rejected recording does not remove its sentence from the pool: the recording is at fault, not the text. A faulty sentence is raised through a proposal instead.
BR-17Rejecting a recording requires at least one reason; approving one may not carry a rejection reason.
BR-18A speaker may report or propose a correction only on an approved sentence that has no recordings yet, and a sentence may have at most one pending proposal.
BR-19While a proposal is pending, its sentence is held out of the recording queue; resolving the proposal returns it.
BR-20A work item claimed from a queue is released automatically after 30 minutes.
BR-21A campaign target must be between 2,000 and 5,000 sentence pairs, and its start date may not be after its end date.
BR-22A campaign must have an assigned Task Manager before tasks can be created in it.
BR-23A task inside a campaign must share the campaign's topic, must fall inside the campaign's date window, and the sum of its target with its sibling tasks may not exceed the campaign target.
BR-24Only a Task Manager may be assigned to own a campaign; only a Task Manager or Administrator may create tasks.
BR-25A recording task may be assigned only to Speakers and a review task only to Reviewers.
BR-26Individual quotas on a task must sum exactly to the task target.
BR-27Reaching the target does not close a task to further work: the target measures progress, it does not lock the work. Only cancelling a task stops it.
BR-28A sentence pair counts as completed for a task only when both of its recordings are approved.
BR-29A dataset may contain only approved recordings.
BR-30Once a dataset is released its contents are immutable.
BR-31Changes to users, sentences, recordings, reviews, tasks, campaigns, proposals and datasets are recorded in the audit log.
