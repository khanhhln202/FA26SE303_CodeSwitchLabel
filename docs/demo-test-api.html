Điểm kỹ thuật nổi bật

  • Database tự giữ luật. Lược đồ nhóm chốt có 8 trigger: chốt đa số sau ba lượt duyệt, chặn tự duyệt, mỗi cặp câu một người đọc, lỗi nội dung đưa câu về duyệt lại, tự ghi nhật ký kèm người thao tác. Backend không tự đặt trạng thái bản ghi: ghi lượt duyệt rồi đọc lại kết quả.
  • Ba lượt duyệt mù. Không ai thấy ý kiến người khác khi bản ghi chưa chốt, kể cả qua API lịch sử. Hai người bấm cùng lúc thì khoá hàng bằng SELECT … FOR UPDATE và so vòng client đã thấy (expectedRound): người đến sau nhận 409 round_changed.
  • Âm thanh. Nhận file trình duyệt ghi ra (WebM, M4A, WAV), ffmpeg chuyển sang WAV 16 kHz mono, đo thời lượng trên file đã chuyển rồi kiểm tra theo ngưỡng cấu hình. File nằm trong MinIO, người nghe nhận link tạm 15 phút.
  • Task tự chạy trạng thái Draft → Open → InProgress → Completed. Chỉ tiêu thu âm đếm theo cặp câu: một cặp chỉ xong khi cả hai bản được duyệt đạt.
  • Tài khoản. Mật khẩu băm bcrypt. Khoá, đổi vai hay đổi mật khẩu có hiệu lực ngay: mỗi request đối chiếu token với database, và token mang dấu của mật khẩu lúc cấp.
  • Lỗi trả về theo một chuẩn (ProblemDetails, RFC 7807) với 58 mã ổn định để FE xử lý. Cả hệ thống chạy bằng một lệnh Docker.

Chuẩn bị trước buổi demo

  1. Mở Docker Desktop. Tại thư mục project, xoá dữ liệu cũ để ID khớp kịch bản. Lệnh này xoá toàn bộ dữ liệu dev.
    docker compose --profile api down -v
  2. Bật cả hệ thống, rồi mở http://localhost:5053 là vào thẳng Swagger. Lần đầu mất vài phút để build.
    docker compose --profile api up -d --build
  3. File test nằm sẵn trong thư mục demo/ của project:
    • input_text_demo.json: 7 câu theo đúng định dạng của cô, 4 câu hợp lệ và 3 câu cố ý sai. Dùng ở màn 2.
    • giong-4s.m4a dài 4 giây, định dạng điện thoại hay ghi. giong-3s.wav dài 3 giây. qua-ngan.wav dài 0,5 giây, để trượt kiểm tra tự động. Dùng ở màn 5 và 8.
    • test-them/: 5 file nhập (một câu, nhiều lỗi, sai cú pháp JSON, mảng rỗng, file văn bản) và 4 file âm thanh (WebM của Chrome, dài 35 giây, file rỗng, file giả). Dùng ở phần bổ sung A và B.
    • Muốn thật hơn thì thu giọng mình bằng Sound Recorder đọc câu “Mình cần review lại phần mã nguồn này” để dùng ở bước 5.2. Riêng bước 8.4 vẫn dùng giong-4s.m4a vì file phải ngắn hơn 5 giây.
  4. Mở mỗi tài khoản một tab Swagger, vì mỗi tab giữ token riêng. Đăng nhập bằng POST /api/auth/login, chép accessToken, bấm Authorize và dán vào, không gõ chữ “Bearer”. Mật khẩu mọi tài khoản: Codeswitch@2026.
  5. Mở sẵn một cửa sổ terminal để kiểm tra database, xem mục ngay dưới.
  6. Bấm nhầm hay làm lệch thứ tự thì chạy lại bước 1 và 2 rồi làm lại từ đầu, mất khoảng một phút.

Cách kiểm tra dữ liệu đã lưu

API trả 200 chưa đủ để chứng minh dữ liệu đã nằm trong database. Mỗi bước có ghi dữ liệu trong kịch bản có mục Kiểm tra dữ liệu đã lưu, bấm vào để mở, kèm câu lệnh và kết quả đúng khi chạy thử.

Gọi lại API

Thứ frontend thấy. Ví dụ nhập file xong thì GET /api/scripts?status=PendingValidation phải ra đủ các câu vừa nhập.

Hỏi thẳng database

Mở psql một lần, rồi dán từng câu SQL trong kịch bản vào:

docker exec -it csl-postgres psql -U csl -d codeswitchlabel

Gõ \pset pager off để kết quả dài không dừng lại chờ bấm phím. \dt liệt kê các bảng, \q để thoát. Chữ tiếng Việt bị lỗi thì thoát ra, chạy chcp 65001 rồi mở lại.

Xem file âm thanh

Vào http://localhost:9090, đăng nhập bằng MINIO_ROOT_USER / MINIO_ROOT_PASSWORD trong docker-compose.yml, mở bucket recordings. Hoặc kiểm tra file đã chuyển sang WAV 16 kHz mono bằng ffprobe trên link nghe:

ffprobe -v error -show_entries stream=codec_name,sample_rate,channels -of default=nw=1 "DÁN_LINK_NGHE_VÀO_ĐÂY"

Tắt máy có mất không

Dữ liệu nằm trong volume của Docker. Tắt rồi bật lại bằng down và up thì vẫn còn; chỉ lệnh có -v mới xoá. Phần bổ sung C chứng minh điều này ngay trước mặt cô.

Kịch bản test API

Chạy đúng thứ tự, vì bước sau dùng kết quả của bước trước. Các ID ghi sẵn chỉ đúng khi database vừa được xoá. Trên Swagger, nhập file có một ô File; nộp bản ghi có bốn ô Audio, ScriptId, SentenceVariant, TaskId.

Cần cô góp ý

  • Khối lượng duyệt. Mỗi cặp câu cần 6 lượt duyệt (hai bản, mỗi bản ba lượt) trong khi nhóm có 4 người. Có khả thi khi thu dữ liệu thật không?
  • Một cặp câu chỉ một người đọc — đúng ý cô chứ? Điều này ảnh hưởng tới độ đa dạng giọng trong dataset.
  • Một người từ chối câu là câu bị loại với mọi người. Có cần Admin xác nhận, hoặc khôi phục được không?
  • Dataset xuất định dạng gì, có kèm alignment và nhãn [vi]/[en] không?
  • Các ngưỡng do nhóm đề xuất, chưa được duyệt: bản ghi dài 1–30 giây. Hai tham số khoảng lặng đầu/cuối có trong lược đồ nhưng hệ thống chưa đo được.
  • Đồng ý cho dùng dữ liệu. Có cần người đọc đồng ý trước khi thu không? Hệ thống lưu giọng nói, năm sinh, tỉnh.
  • Thông báo. Có cần báo cho người đọc khi bản ghi bị từ chối không? Hiện người đọc tự xem lý do trong danh sách bản ghi của mình.
  • Còn phải làm: Reviewer xem danh sách bản ghi trong task, khôi phục câu bị loại, dataset và tải về, Admin quản lý danh mục lý do, giới hạn đăng nhập sai, deploy lên máy chủ (dự kiến 12/2026).
